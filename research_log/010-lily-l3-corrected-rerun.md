### อ่านแบบเร็ว

หลัง B7.3 ใช้ผลไม่ได้เพราะนับสัปดาห์เกินขอบเขต B7.5 จึงล็อกกติกาใหม่ให้ตรวจวันที่และตารางทดลองก่อนอ่านค่าผลตอบแทน B7.6 ได้รับอนุญาตให้ลองรันตามกติกานี้หนึ่งครั้ง แต่ตัวตรวจค้นหาชื่อฟิลด์ `schema` ขณะที่ container ใช้ชื่อ `schema_version` จึงเข้าใจผิดว่า metadata หายและหยุดทันที โปรแกรมอ่านและสแกน raw bytes ของ container แล้ว แต่ยังไม่ได้ถอดรหัสหรือใช้ค่าผลตอบแทน ไม่มีตารางทดลอง ไม่มีผลคำนวณ และไม่มี ledger รอบใหม่

## 2. ปัญหา (คำถาม) และสมมติฐาน

- คำถามวิจัย: ก่อนอ่านค่าผลตอบแทน ตัวตรวจ B7.6 สามารถยืนยันขอบเขตวันและสร้างตารางรายสัปดาห์ของ L-3 ที่ถูกต้องได้หรือไม่
- ขอบเขต: ใช้เฉพาะ container falsification ที่ gate ระบุ ตรวจเพียง schema รายชื่อ ETF ฟิลด์วันที่ ช่วง `2007-02-05` ถึง `2015-12-31` และความครบของช่วงยืนยัน 20 sessions ห้ามถอดรหัสค่าผลตอบแทนก่อน preflight ผ่าน และห้ามเข้าถึง validation
- สมมติฐาน: metadata ใน container น่าจะเพียงพอให้ยืนยันว่า ETF ครบแปดตัว ทุก decision อยู่ในช่วง falsification และทุกช่วงยืนยันสิ้นสุดไม่เกิน `2015-12-31` ก่อนที่โปรแกรมจะอ่านผลตอบแทน
- เกณฑ์ตัดสิน: preflight จะผ่านได้ต่อเมื่อ schema และรายชื่อสินทรัพย์ตรงกับสัญญา ตารางมีไม่เกิน 465 weekly observations ไม่มีวัน validation ปะปน และสร้าง schedule attestation พร้อม hash สำเร็จ หากข้อใดตรวจไม่ได้ โปรแกรมต้องหยุดก่อน return parsing และสรุป `scope_restricted`

งานนี้ไม่ได้ทดสอบสมมติฐานเชิงผลลัพธ์ของ L-3 โดยตรง แต่ทดสอบว่ากลไกป้องกันการเปิดข้อมูลผิดลำดับทำงานได้หรือไม่ หาก preflight ยังไม่น่าเชื่อถือ การทดลองจริงก็ยังเริ่มไม่ได้

## 3. ขั้นตอนการทดลอง

1. ตรวจ activation gate, hash ของ B7.5, runner, report schema และคำสั่งที่อนุญาตให้ลองรันเพียงครั้งเดียว
2. เปิด container ในระดับ raw bytes เพื่อค้นหา metadata ที่จำเป็น โดยออกแบบให้ยังไม่ถอดรหัสฟิลด์ผลตอบแทน
3. ตรวจชื่อ schema ลำดับ ETF แปดตัว และ `session_date` ของแต่ละสินทรัพย์ เพื่อสร้างเฉพาะวันที่ที่ทุกสินทรัพย์มีร่วมกัน
4. จากวันที่ร่วมกัน เลือก weekly decision dates ที่อยู่ในช่วง falsification จับคู่วัน execution ถัดไป และตรวจว่าช่วง realized confirmation 20 sessions จบไม่เกิน `2015-12-31`
5. ตั้งใจให้เขียน schedule attestation และ container identity ก่อนเข้าส่วนคำนวณสัญญาณ แต่หาก metadata ขั้นใดไม่ผ่านต้องหยุดทันที
6. หลัง B7.6 จบ มีการตรวจ provenance เพิ่มใน B7.7 โดยไม่เปิด container ซ้ำ เพื่อบันทึกให้ชัดว่าขั้นตอนไหนอ่านข้อมูลไปแล้วและเหตุใด hash จึงไม่ถูกเก็บไว้

## 4. ผลลัพธ์

B7.6 หยุดที่ข้อผิดพลาด `date_only_schema_metadata_missing` ก่อนเข้าสู่ return parsing รายงานจึงไม่มี observation counts, primary statistics, realized confirmation, side effects หรือคำตัดสินเชิงสมมติฐาน

การตรวจภายหลังพบว่าสาเหตุไม่ใช่เพราะ container ไม่มี schema แต่เป็นเพราะ implementation ค้นหาฟิลด์ `schema` ขณะที่ข้อมูลจริงใช้ `schema_version` ตัวตรวจจึงรายงานว่า metadata หายทั้งที่เป็นความไม่ตรงกันของชื่อฟิลด์ระหว่างสัญญากับโปรแกรม

หลักฐาน provenance ที่เพิ่มภายหลังระบุว่า B7.6 อ่านและสแกน raw container bytes แล้ว แต่ไม่ได้ถอดรหัสหรือใช้ค่าผลตอบแทน จำนวน market-return values ที่อ่านจึงเท่ากับ `0` อย่างไรก็ตาม เส้นทาง exception ทิ้ง container hash ที่คำนวณระหว่างความพยายามนั้น ทำให้รายงานเก็บ `container_sha256` เป็น `null` และไม่สามารถกู้ hash ของ attempt เดิมย้อนหลังได้อย่างน่าเชื่อถือ

เพราะ preflight ไม่ผ่าน จึงไม่มี pre-return schedule attestation, ไม่มี schedule hash, ไม่มี real-return decision run และไม่มี ledger แถวใหม่ ข้อมูล validation ช่วง `2016-01-04` ถึง `2026-06-30` ยังคง `sealed_not_accessed`

## 5. อภิปรายผล ปัญหา และข้อจำกัด

ผลนี้บอกว่ากลไกก่อนอ่านผลตอบแทนของ B7.6 ยังใช้งานไม่ได้ แต่ไม่ได้บอกว่า container เสียหรือข้อมูล L-3 ไม่เพียงพอ ความล้มเหลวเกิดจาก data contract ระหว่างโปรแกรมกับ container ไม่ตรงกันเพียงชื่อฟิลด์เดียว และเส้นทางจัดการข้อผิดพลาดไม่เก็บ provenance ที่ควรเก็บ

การหยุดก่อนถอดรหัสผลตอบแทนเป็นพฤติกรรมที่ถูกต้องเมื่อ preflight ไม่แน่ใจ สิ่งที่ผิดคือโปรแกรมแยกไม่ออกระหว่าง “metadata ไม่มีจริง” กับ “โปรแกรมค้นหาชื่อผิด” รวมทั้งไม่รักษา attempted hash ไว้สำหรับการตรวจย้อนหลัง

B7.7 พยายามแก้เครื่องมือส่วนนี้ด้วยข้อมูลสังเคราะห์เท่านั้น แต่การตรวจอิสระภายหลังยังพบช่องว่างใน validation-date guard, report validator และ report schema จึงยังไม่ถือว่าเครื่องมือพร้อมสำหรับการรันใหม่ การแก้เครื่องมือไม่ได้ให้อำนาจเปิด container หรือทดลองซ้ำโดยอัตโนมัติ

สิ่งที่ห้ามสรุปจากการทดลองนี้:

- ห้ามสรุปว่า L-3 ถูกหักล้างหรือยังไม่ถูกหักล้าง เพราะไม่มีผลทดลองเชิงสมมติฐานเกิดขึ้น
- ห้ามสรุปว่า inverse-volatility sizing ลดความเสี่ยงหรือทำกำไรได้
- ห้ามตีความ failure code ว่า container ไม่มีข้อมูลหรือ provider ส่งข้อมูลผิด
- ห้ามอ้างว่า B7.7 อนุญาต rerun หรือทำให้ report contract ผ่านการตรวจแล้ว
- ห้ามเปิดหรือรวมข้อมูล validation กับการแก้ปัญหาเครื่องมือครั้งนี้

## 6. สรุปผลการทดลองและแนวทางพัฒนาต่อ

ข้อสรุป: `จำกัดขอบเขต` B7.6 ไม่สามารถยืนยันตารางก่อนอ่านผลตอบแทนได้ เพราะโปรแกรมค้นหาชื่อฟิลด์ schema ผิด แม้จะสแกน raw bytes ของ container แล้ว แต่ยังไม่ได้ถอดรหัสผลตอบแทนและไม่ได้สร้างผล L-3 ใด ๆ

แนวทางพัฒนาต่อ:

1. แก้ data contract ด้วย artifact รุ่นใหม่โดยเก็บ B7.6 และ B7.7 ไว้เป็นประวัติ ห้ามแก้ locked files เดิม
2. ให้ scanner ปฏิเสธวันที่ตั้งแต่ `2016-01-04` หากพบในสินทรัพย์แม้เพียงตัวเดียว ไม่ใช่ตรวจเฉพาะวันที่ร่วมกันทั้งแปดตัว
3. ให้ report schema และ validator ตรวจ nested evidence, producing commit, gate hash, container identity, schedule, ledger และ decision logic แบบ fail-closed พร้อม adversarial tests
4. รักษา container hash และเหตุผลที่หยุดไว้แม้เกิด exception โดยไม่เปิดเผยค่าผลตอบแทน
5. ห้าม rerun จนกว่า Inspector จะยอมรับเครื่องมือรุ่นใหม่และเจ้าของอนุมัติคำสั่งทดลองใหม่แยกต่างหาก
